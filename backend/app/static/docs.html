DocuPulse IDP — Technical Documentation

Architecture, design, database, deployment and operations guide for DocuPulse IDP, an intelligent document processing application that runs entirely on your own network: no cloud services and no internet access are needed at run time.

1. Introduction

DocuPulse IDP turns documents (PDFs, scans, photos, text files) into structured data. Users upload a document; the system reads its text (from the PDF text layer or by offline OCR), recognises what kind of document it is, extracts fields and tables, checks them, and routes anything uncertain to a person for review. Reviewers can correct values, add fields by drawing on the page, and save the result as a reusable template so similar documents are extracted the same way next time.

Fully offlineText extraction, OCR, rules and templates run locally. No LLM is required; an optional local LLM on your own network can be enabled.
Any documentBuilt-in rules for contracts, passports/IDs and invoices; templates for your own forms; a general extractor for everything else.
Human in the loopLow-confidence or invalid values go to review with the source highlighted on the page; every change is audited.
Enterprise sign-inLocal accounts, Okta (OIDC) or Active Directory/LDAP, with AD-group based roles and per-user document isolation.

Key capabilities

  • Upload PDF (text or scanned, multi-page), PNG/JPG/TIFF/BMP/WEBP images, TXT/MD/CSV/JSON. Maximum size configurable (default 25 MB).
  • Auto-detection of document type and matching template; ICAO 9303 passport MRZ validation (all five check digits); invoice reconciliation (subtotal + tax = total, line items = subtotal).
  • Layout-aware extraction of label/value pairs (with or without colons), multi-column forms, and tables including wrapped cells and tables spanning pages.
  • Document Hub with Finder-style folders (nested, drag-and-drop, up to three favourite folders as tabs) and multi-select move/delete.
  • Review Studio: page viewer with value boxes, inline editing, draw-to-add fields (also by touch), field renaming, approve/reject, audit trail.
  • Web UI in Angular: responsive on phone, tablet and desktop, installable as an app (PWA), six colour themes with light, dark or automatic mode.
  • Security: sign-in lock-out, temporary first-run admin password, strict security headers, encrypted stored secrets, JSON application and audit logs with request ids (section 7).
  • Exports: JSON, CSV and Excel (.xlsx, one sheet for fields and one per table). Webhooks with HMAC-SHA256 signatures. REST API with API keys.
  • Database: SQLite (default), PostgreSQL or Microsoft SQL Server, selected by configuration.

2. Architecture

DocuPulse has three layers that can be deployed together or separately:

  • Web UI — a static Angular build (frontend/dist): a responsive, installable web app (PWA) that works on phones, tablets and desktops. It talks to the system only through the REST API, at the address set in config.js. It can be hosted by the API server itself or by any web server (IIS, nginx, Apache).
  • API server — one Python process (FastAPI on Uvicorn) with the REST API, sign-in and the document-processing engine. Settings in backend/config/server.ini.
  • Database — SQLite on the API server, or SQL Server / PostgreSQL on their own server. Settings in backend/config/database.ini.

2.1 Web UI on phones, tablets and desktops

  • Responsive: below 900 px wide the sidebar becomes a slide-out menu (☰ in the header); below 640 px document lists turn into cards, forms use one column, dialogs open as bottom sheets and the Review Studio stacks the page above the fields. Drawing a box to add a field works with touch.
  • Installable (PWA): browsers offer Install app / Add to Home Screen. The installed app opens in its own window and its screens load from the device even when the server is unreachable; documents and every other API response always come live from the server and are never cached on the device.
  • Install needs HTTPS: browsers only allow installing (service workers) on https:// addresses or on localhost. On a plain http://server:8000 intranet address the app works normally in the browser but is not installable; put it behind the TLS reverse proxy in 11.6 to enable install.
  • Themes and light/dark mode: the user menu (top right) has Appearance: Light, Dark or Auto (follows the device's setting and switches with it), and six colour themes — Ocean (white and blue, with a blue sidebar in light mode), Indigo (the default), Emerald, Violet, Sunset and Graphite — each in a light and a dark version. The choice is saved in the browser on that device (localStorage key idp-appearance), so each person and device can have their own; nothing is stored on the server. Colours are CSS custom properties in frontend/src/styles.css (section "Themes"); a new theme is one block there plus an entry in core/theme.ts.
  • Updates: after a new build is deployed, an open or installed app picks it up on its next load (index.html, ngsw.json, ngsw-worker.js and config.js are served uncached).

Files (uploads, page images) live on the API server's storage folder, which can be a network share. External systems are optional and only used if configured.

Design principles

  • Offline by default. No CDN, no web fonts from the internet, no cloud APIs. Fonts, OCR models and the API docs are bundled.
  • Never invent data. A value that is not found is left empty and flagged; it is never filled with a guess.
  • Deterministic first. Rules, layout analysis and templates do the work; an LLM is optional and can only return values that literally appear in the document.
  • Isolation enforced on the server. Every document request checks ownership; the UI hiding something is never the only control.
  • Layered and configurable. The UI only talks to the API; the API only talks to the database through its connection settings. Any tier can move to another server by editing a settings file, with no code change or rebuild.

4.2 Request handling

Every /api/v1 endpoint depends on check_scope(...), which calls verify_api_key: a request is identified either by the idp_session cookie (browser) or by an X-API-Key / Bearer header. Anonymous requests receive 401. The caller's role defines its scopes; an API key can only narrow its owner's scopes.

RoleScopesCan do
userdoc:read doc:writeUpload, review, edit, export and delete own documents; save a template from own document; pick templates.
admin+ schema:manage adminAll of the above for own documents, plus templates, users, sign-in settings, API keys, webhooks, API reference.

Per-document endpoints call _owned(doc_id, auth) first: if the document's owner_id is not the caller, the response is 404 Document not found — identical to a missing document, so other users' document IDs cannot be probed. This applies to read, page images, exports, edits, re-run, approve/reject and delete. Lists and dashboard figures are filtered by owner in SQL.

4.3 Processing model

Uploads are processed synchronously by default (sync=true, the response contains the finished document) or in the background (sync=false, status queued → processing → result; clients poll or listen to webhooks). CPU-heavy steps (rendering, OCR) run in a worker thread so the API stays responsive. Webhooks are dispatched as background tasks so a slow receiver never delays processing.

StatusMeaning

needs_reviewA field failed validation, overall confidence is below the threshold (default 85%), no text or no fields were found, or no template matched

5. Extraction pipeline

5.1 Reading text

  • PDF with a text layer: pdfplumber returns text and word boxes; coordinates are stored as percentages of the page so overlays work at any zoom.
  • Scanned page (fewer than 20 characters of text) and images: the page is rendered at 200 dpi and read by RapidOCR. OCR output gets spacing repair (e.g. ShipTo:Warehouse4 → Ship To: Warehouse 4).
  • Every page is also rendered to PNG (2x) for the Review viewer.

5.2 Layout analysis

Words are grouped into visual lines; each line is split into segments wherever the gap is clearly wider than the usual word space (2.2× the median small gap, minimum 1% of page width) or the font size changes. Segments keep side-by-side columns apart, so an address on the left never merges into a Room: label on the right.

5.3 Classification and routing

  • Built-in types are scored by vocabulary (e.g. invoice, subtotal, bill to); an MRZ line forces identity.
  • Templates are scored by how many of their labels/aliases appear, combined with the letterhead fingerprint (first lines of the sample they were saved from). A template built on a contract/passport/invoice also needs ≥ 75% fingerprint match, so another vendor's invoice does not pick up the wrong template.
  • Upload type auto uses the best match; generic, a built-in type, or a specific template can be forced. Re-run lets a reviewer apply a different choice later.

5.5 General extractor

  • Label: value pairs per layout segment, including several per line, with exact value boxes.
  • Form layouts without colons (label, wide gap, value), with safeguards for bilingual header rows and table rows.
  • Named people (Mr./Mrs./Dr. …), dates, amounts, emails, phones, URLs and reference numbers as additional entities.
  • Values are typed (date → ISO 8601, amounts and numbers → numeric, email).

5.6 Tables

A table starts at a header row of three or more short, non-numeric titles. Each column owns the strip from just left of its title to the next title. Following lines are assigned cell by cell; a line with no digits that sits within one row-gap below is merged into the row above (wrapped cells). The table ends at a clear vertical gap or a non-table line, and continues on the next page with or without a repeated header.

5.7 Optional local LLM

Disabled unless LOCAL_LLM_URL is set (any OpenAI-compatible server on your network). It is asked only for template fields the rules did not find; an answer is kept only if that exact text occurs in the document, is marked local_llm and is always flagged for review.

6. Templates & review

A template (table custom_schemas) lists the fields a document type has. Each field may carry a label, aliases, data type, required flag, confidence threshold, regex, allowed values, and a page region. Templates are created in Templates (admins), or by anyone from Review → Save as Template.

Field attributeEffect
regex_patternTried first; group 1 (or the whole match) is the value

6.1 Lookup API (a template's own endpoint)

In Templates → Edit (pencil) → API, an administrator can publish a lookup endpoint for the template. Other applications then find documents of that template and read their fields as JSON, without knowing DocuPulse's document model.

  • Endpoint name: suggested from the template name (US Passport Details → getUsPassportDetails) until you type your own. It starts with a letter, uses letters, digits and _ (3–64 characters) and is unique across active templates, ignoring case. Stored in custom_schemas.api_endpoint / api_enabled.
  • Search keys: tick Search on each field that may be looked up (stored as api_search on the field). The query parameter is the field name in camelCase (last_name → lastName; the field name itself also works). Lookup by documentId is always available. A field whose parameter would be documentId, limit or offset (e.g. a field named document_id) cannot be a search key; rename it (e.g. reference_number).
  • Sensitive: tick for personal data such as an SSN or date of birth (suggested automatically for names like ssn, tax, birth, passport_no, account). See the rules below.
  • Calls: GET /api/v1/lookup/<name>?lastName=Doe&firstName=Jane or POST /api/v1/lookup/<name> with {"ssn": "123-45-6789"}. GET /api/v1/lookup lists the published endpoints. Each one is also listed with its parameters in the API reference (section 9) and in the API Developer Portal, with a copyable example.

Document Hub folders

  • Works like Finder: New Folder creates one in the folder you are in (folders can nest), and a path bar (All Documents › Invoices › 2026) leads back up. The open folder is part of the address (/documents?folder=…), so Back/Forward and bookmarks work.
  • Upload: the dialog's Save to folder starts at the folder open in the Document Hub (top level elsewhere), and can create a folder. Documents uploaded with no folder stay at the top level.
  • Move documents by dragging them (or all checked ones) onto a folder or a path segment, or with Move to… after checking them (also on phones). Folders can be dragged into other folders.
  • Rename a folder in place. Deleting a folder never deletes documents: its documents and subfolders move up to where the folder was.
  • The row above the list holds All Documents (the top level), up to three favourite folders and Templates (documents read with a template, from every folder). An empty slot reads + Favourite folder and lists folders to pin; the × on a favourite unpins it, and each folder row has a Favourite / Unpin button. Favourites are saved per user on the server (folders.favorite_rank), so they follow you to other devices.
  • Search looks in every folder and shows where each match is. Folders are private to their owner, like documents.

Review Studio

  • Drag a box anywhere on the page to add a field: the text inside becomes the value, and the label beside or above becomes its name (editable at once). Click any field name to rename it; the printed label is kept as an alias for templates.
  • Only changed values are saved; each change records old and new value in the audit trail with the signed-in user.
  • Export (Excel or CSV) saves pending edits first. Delete removes the record, file, page images and audit trail.

8. Database design

Twelve tables; all identifiers are text (prefixed IDs such as doc_…, usr_…, schema-…). Timestamps are ISO 8601 strings in UTC. Flexible structures (fields, metadata, settings) are stored as JSON text so the schema is identical across SQLite, PostgreSQL and SQL Server. Relationships are enforced by the application rather than foreign-key constraints, so documents can be deleted without cascades blocking and the same SQL runs on all three databases.

9. API reference

All endpoints are under /api. Authenticate with the browser session or an X-API-Key header. Machine-readable spec: /openapi.json. The list below is generated live from the running server.

Errors are JSON: {"detail": "…", "request_id": "…"}; validation errors (422) add "errors": [{"field": "…", "problem": "…"}] without echoing values; 500 errors carry only a generic message and the request_id. 11.8 Configure sign-in

The sign-in method is chosen in backend/config/auth.ini (created from auth.example.ini on first start), read at every start:

[signin] modeMeaning
local (default)Usernames and passwords managed in the app
ldapActive Directory / LDAP with the [ldap] settings in the file
oktaOkta with the [okta] settings in the file
uiThe file is ignored; administrators choose the method in Admin Settings → Users & Sign-in
  • The file wins. With local, ldap or okta, each start writes the method and its settings into the database, and Admin Settings shows them read-only with the file's location (an attempt to change them through the API gets 409). Group roles stay editable in Admin Settings unless the file's [roles] section lists groups. A file left untouched means Local sign-in.
  • Secrets go in environment variables: IDP_OKTA_CLIENT_SECRET, IDP_LDAP_BIND_PASSWORD (they override the file; an empty value keeps the one already stored). They are stored encrypted (7.1). Any other key can be overridden the same way: IDP_AUTH_MODE, IDP_OKTA_ISSUER, IDP_LDAP_SERVER_URL, …
  • Incomplete settings (e.g. mode = okta without an issuer) are reported as an error in app.log at start; only local administrators can sign in until the file is fixed.
  • The local admin account always works as a backup login, in every mode.

Example for Active Directory:

[signin]
mode = ldap

[ldap]
server_url = ldaps://dc01.corp.local:636
bind_dn = CN=svc-idp,OU=Service Accounts,DC=corp,DC=local
user_base_dn = DC=corp,DC=local

[roles]
IDP-Admins = admin
IDP-Users = user
default_role = none

# and in the service's environment:  IDP_LDAP_BIND_PASSWORD=…

With mode = ui, configure it in the app instead:

  1. Sign in as the local admin → Users & Sign-in.
  2. AD/LDAP: server ldaps://dc01.corp.local:636, search base, service account, filter (&(objectClass=user)(sAMAccountName={username})). Use Test directory with a real user; it shows their groups and resulting role.
  3. Okta: create an OIDC Web app, add redirect URI https://idp.corp.local/api/auth/okta/callback, add a groups claim; enter issuer, client ID/secret; Test Okta connection.
  4. Group roles: map e.g. IDP-Admins → Admin, IDP-Users → User; choose whether people in no mapped group are refused.
  5. Switch the sign-in method and save. The local admin keeps working as a backup.

Running several API servers behind a load balancer

  • No sticky sessions needed. Sign-in sessions live in the database, and an Okta sign-in in progress travels in a short-lived encrypted cookie, so any instance can answer any request.
  • One database (SQL Server or PostgreSQL; SQLite is for a single server only) and one shared storage folder: point [storage] dir on every instance at the same NFS/SMB share (uploads, page images, secret.key). With IDP_SECRET_KEY set instead, use the same value on every instance.
  • Same configuration everywhere: copy server.ini and database.ini to each instance; set host = 0.0.0.0 (or the instance IP) and list the load balancer's addresses in [security] trusted_proxies.
  • Health check: GET /api/health (no sign-in, 200 when ready).
  • Forward headers from the load balancer: Host (the public hostname), X-Forwarded-For, X-Forwarded-Proto and optionally X-Request-ID. nginx: 
    upstream idp_api { server 10.20.1.21:8000; server 10.20.1.22:8000; }
server {
  listen 443 ssl; server_name idp.corp.local;
  client_max_body_size 30m;
  location / {
    proxy_pass http://idp_api;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Request-ID $request_id;
    proxy_read_timeout 300s;   # large scanned PDFs take a while with sync=true
  }
}
  • Upgrades: a release that changes the database upgrades it on start. Start one instance first, wait for /api/health, then start the rest.
  • Per-instance limits: sign-in lock-out counters are kept per instance, so with N instances a guesser gets at most N × the limit before every instance locks; lower login_max_failures if that matters. Logs are written per instance ([logging] dir, or forward them to your SIEM).

Checklist: changing a hostname, port or IP

  1. DNS: point the new name at the server or load balancer; issue a TLS certificate for it.
  2. Reverse proxy / load balancer: server_name, certificate, upstream IPs and ports.
  3. API port or interface changed: server.ini [server] host / port, the proxy's upstream, firewall rules.
  4. UI on its own address: config.js apiBaseUrl (if the API moved) and server.ini [cors] allowed_origins + [frontend] frontend_url (if the UI moved).
  5. Proxy IPs changed: server.ini [security] trusted_proxies.
  6. Okta in use: update the redirect URI in Admin Settings and in the Okta app (both must match the public API address).
  7. Database moved: database.ini host/port (and the database firewall).
  8. Restart the API service(s); check /api/health, sign in, open a document. Users sign in again on a new hostname (cookies are per host); the installed app (PWA) must be reinstalled from the new address.

On the tunnel, add a public hostname (newer dashboards call it a Published application route; not "Hostname routes", which are private-network only) on a domain in your Cloudflare account (e.g. docupulse.example.com), service HTTPS → web:443, and under TLS turn on No TLS Verify (the container's certificate is self-signed; visitors get Cloudflare's trusted certificate).
  3. On the NAS put the token in .env (CLOUDFLARE_TUNNEL_TOKEN=..., file mode 600), then docker compose --profile public up -d. Stop public access with docker compose stop tunnel (or delete the public hostname in Cloudflare).

Nginx takes the visitor's address from CF-Connecting-IP only when the request comes from the tunnel container (IDP_TUNNEL_IP), so logs and sign-in lockouts see real visitors and nobody on the LAN can fake the header. Before going public: change the admin password (forced at first sign-in), keep [features] demo_presets = false, and create a local account per tester in Admin Settings → Users (each sees only their own documents). Optionally put a Cloudflare Access policy (email one-time code) in front of the hostname so only invited people reach the sign-in page.

Operate: docker compose ps (both show healthy), docker compose logs -f api, docker compose restart. Upgrade: docker load the new bundle, set IDP_VERSION, docker compose up -d; data/ is kept and database upgrades run on start. Back up: docker compose stop, copy data/, docker compose start (or the SQLite online backup from section 14 while running).

13. Operations & monitoring

  • Health: GET /api/health (no sign-in) returns status, version, OCR engine, database engine, whether a local LLM is configured and whether the server also serves the UI. Use it for load-balancer and uptime checks.
  • Logs (in [logging] dir, default backend/storage/logs/, rotated at 20 MB × 10 files):
    • app.log — start-up, one line per request (method, path without query string, status, milliseconds, user, client address), warnings and errors with stack traces. Also printed to the console (journald / docker logs).
    • audit.log — always JSON: login (success / failure / blocked / denied, with method and reason), logout, password_change, admin.auth_settings_changed (which sections; never secret values), admin.user_created, admin.user_changed, and api_change for every POST/PUT/PATCH/DELETE (method, path, status, actor).
    • Every line has time (UTC), level, request_id, user and client_ip. The same request id is returned to the browser in X-Request-ID and in error responses ("reference …"), so a user's report leads straight to the log lines. A request id sent by nginx (proxy_set_header X-Request-ID $request_id;) is reused.
    • Never logged: passwords, session tokens, API keys, secrets, query strings, document text or extracted values. A filter masks anything credential-like as a safety net.
    Example: 
    {"time": "2026-10-24T21:55:44.099+00:00", "level": "INFO", "logger": "idp.audit", "message": "login", "request_id": "fcca45b5c5164fb0", "user": "-", "client_ip": "10.1.4.22", "event": "login", "outcome": "failure", "username": "jdoe", "reason": "wrong password", "method": "ldap"}
  • What to watch: share of failed documents, the review rate on the dashboard, disk usage of storage/, webhook failures (Admin → Webhooks → delivery logs), sign-in failures and lock-outs ("event": "login" with "outcome": "failure" or "blocked" in audit.log), and ERROR lines in app.log.
  • Housekeeping: expired sessions are purged automatically; delete old documents via the document list (multi-select) or the API; rotate API keys periodically.

15. Upgrades

  1. Back up the database and storage (section 14).
  2. Stop the service; replace the application files (keep backend/storage — including secret.key — and backend/config/: server.ini, database.ini, auth.ini). New settings sections are optional; compare with the .example files.
  3. Install new packages offline (pip install --no-index --find-links wheels -r backend/requirements.txt). Upgrading from 1.3 or earlier: 1.4 needs Python 3.11+ (3.12 recommended): recreate venv with the new Python before installing (the install script does this when venv is removed).
  4. With several API servers, start one first, wait for /api/health, then the others.
  5. Docker / NAS: docker load -i docupulse-idp-images.tar.gz from the new bundle, set IDP_VERSION in .env, docker compose up -d (section 11.10). Steps 2 and 3 do not apply.
  6. Start the service. A release that changes the database includes the upgrade; it is applied once on start and recorded in schema_version.

17. Known limitations

Tested in development on macOS with SQLite. The Mac/Linux scripts were run with macOS bash and the Windows PowerShell scripts with PowerShell 7 on macOS; neither has yet run on an actual Linux or Windows server. PostgreSQL, SQL Server, Okta and AD/LDAP have not yet been tested against real servers (LDAP was tested against a simulated directory). Validate each in a test environment before go-live.
  • Several API servers can run behind a load balancer (11.9) with one shared database and storage folder; documents are processed inside the API server that received them. Sign-in lock-out counters are kept per server.
  • OCR quality depends on scan quality; handwriting is not supported. The bundled OCR model is tuned for Latin and Chinese scripts.
  • Numeric dates such as 05/10/2026 are read month-first (US).
  • Word/Excel uploads (.docx, .xlsx) are not accepted; convert to PDF first.
  • Documents and folders belong to their uploader only; there is no sharing between users or team folders yet. Lookup endpoints follow the same rule: a key finds only its creator's documents.
  • Lookup endpoints compare values in the API server, over the caller's approved documents of that template; fine for tens of thousands of documents per user, not built for millions. There is no per-key rate limit beyond the quota.
  • Webhook signing secrets are stored as entered (the server needs them to sign); the Okta client secret and LDAP service password are encrypted.
  • Installing the web UI as an app (PWA) needs HTTPS (or localhost).
